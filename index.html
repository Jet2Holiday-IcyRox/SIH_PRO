One health identity.
Consent on every single share.

AyurFHIR Bridge issues an ABHA identity from Aadhaar eKYC, links medical records to it as FHIR R4 bundles dual-coded in NAMASTE and ICD-11 TM2, and brokers every hospital access through a consent artifact the patient signs — and can revoke mid-session.

Try it yourself — 3 steps, no setup

Everything is a working demo. Nothing you do here touches real patient data.

account_tree Federated ABDM Architecture — no central record store

Identity, consent, and data disclosure are three separate, independently enforced layers.

REST · FHIR R4 · HIE-CM
fingerprint

1 · Identity (ABHA)

Aadhaar Verhoeff check → OTP eKYC → 14-digit ABHA number + @sbx address. Aadhaar is never persisted.

link

2 · Care Contexts

HIP pushes a link request; the patient approves it. Records are FHIR R4 Bundles carrying NAMASTE + ICD-11 TM2 codings.

how_to_reg

3 · Consent (HIE-CM)

Every HIU request creates a fresh artifact: purpose code, HI-types, date range, expiry. Patient signs it with OTP.

policy

4 · Disclosure + Audit

Only the consented slice is disclosed — to a hospital under CAREMGT, to an insurer under HPAYMT. Reads die instantly on revoke or expiry, enforced in database rules — not in UI code.

Where enforcement actually lives

shield_lock

Disclosure reads are gated server-side. disclosures/{consentId} is readable by the requesting HIU only while the parent consent is GRANTED and expiryAt > now. Revoking flips one field and every subsequent read fails — even for a client that already has the consent ID cached.

history_toggle_off

Access logs are append-only. The write rule requires !data.exists(), so a log entry can never be edited or deleted — including by the hospital that created it, or by an admin.

swap_horiz

Consent state machine is validated. Only REQUESTED→GRANTED/DENIED and GRANTED→REVOKED/EXPIRED are legal transitions, and only the patient can make them. A HIU cannot self-approve its own request.

person_off

Identity cannot be forged. A consent's patientUid must equal the real owner of the referenced ABHA, cross-checked against abha/{key}/ownerUid at write time.

            report Not production-ready — deliberately
          

          
Consent artifacts here are hash-stamped, not cryptographically signed by a national CA; the OTP is generated client-side because there is no SMS gateway; and a real ABDM integration requires a server-side proxy holding client_id/client_secret, which must never sit in browser code. The ABDM_ADAPTER boundary in this file is exactly where that proxy plugs in — everything above it, including all consent enforcement, is already faithful to the HIE-CM specification.
